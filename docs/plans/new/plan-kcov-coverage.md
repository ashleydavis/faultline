# Coverage from kcov as an alternative to annotating every branch

## Overview

Faultline decides which code paths a function has by parsing it (`src/framework/coverage.zig` walks the AST and lists an entry path, both sides of every `if`, every `switch` arm, every loop body, every `catch` and `orelse` fallback), and today it learns which of them ran only from `if (an) annotate(...)` calls the project writes into each branch. That puts a line in every branch of every function before a project sees a number, and a function with no `Log` parameter can never be ticked at all. This plan adds a second source of ticks: line coverage read from kcov, which watches the simulation binary from outside through its DWARF line table and needs no change to the code under test. Every path gets a witness line, the line whose execution proves that path ran, and a path is ticked when either its annotation came back or kcov saw its witness line. Annotations stay as they are and keep working; kcov makes them unnecessary for every branch whose body sits on a line of its own. The run becomes a loop of rounds: the run process spawns kcov around a worker copy of itself, reads the coverage kcov wrote when the worker exits, ticks the checklists, and runs another round for only the functions that still have a path to reach, stopping the moment every path is ticked or a round reaches nothing new.

## Notes

- kcov reports each address at most once per process: its ptrace engine clears a breakpoint the first time it is hit (`clearBreakpoint(ev.addr)` in `src/engines/ptrace.cc`) and its cobertura writer normalises `hits` to 1 for single-hit parsers. So line coverage says whether a line ran, never how many times, and the false side of an `if` with no `else` whose true side carries on cannot be told apart from the true side by lines. That case keeps today's counting through the annotation on the true side. Where the true side returns, breaks or continues, the statement after the `if` is the witness and no annotation is needed.
- kcov follows forked and cloned children (`PTRACE_O_TRACECLONE | PTRACE_O_TRACEFORK | PTRACE_O_TRACEVFORK` in `src/engines/ptrace_linux.cc`), which the run depends on because every call is made in a forked child. Step 3 confirms this on a real run before anything is built on it.
- kcov's JSON output holds per-file percentages only; the per-line data is in the cobertura XML, which is why the reader parses that. `--cobertura-only` writes it as `cov.xml` in the output directory (the option's own help text). kcov accumulates into an output directory across runs unless `--clean` is passed; the plan uses one directory per round instead, so what a round added is readable on its own.
- Optimised builds may have no line-table entry for a statement the optimiser folded away, which is why `LineSet.isCode` exists and why step 3 measures `ReleaseSafe` against `Debug`. The worker's optimisation mode is decided by that measurement, not here.
- A round is the unit of feedback: the run learns what ran only when kcov writes its output at the worker's exit. Reading kcov's periodic output mid-run (`--output-interval`) would give finer feedback at the cost of parsing the whole report repeatedly while it is being written, and was rejected for that.
- The in-process quiet-stop in `exerciseFunction` (`quiet_calls_before_stopping`) still applies inside a round for functions that annotate; a function with no annotations runs its full trial count in each round it is listed in. Rounds after the first list only the functions with a path still unticked, which is where the saving comes from.
